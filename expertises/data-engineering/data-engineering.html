Trigger moments

You do not need another data project. You need a reason to stop reconciling the same decision twice.

Two dashboards, one question

A correction with no durable explanation

Every workload creates another exception

Scope boundary

Data engineering first. Adjacent mechanisms only when the decision requires them.

In

Data modelling, ingestion, ETL/ELT, quality gates, event/state records, lineage, provenance, evidence stores, auditable APIs, replay and handoff.

Out by default

Wholesale platform migration, business-semantic arbitration without owner, blockchain as decoration, security certification, regulatory certification, guaranteed ROI, unsupported “faster/cheaper” claims.

Process

Inventory → foundation → controls → handoff.

1. Inventory

Choose the decision, enumerate sources/rules/owners, record current failure and baseline.

2. Foundation + controls

Define contracts and transformations, implement lineage/quality instrumentation, test representative failure boundaries.

3. Handoff

Document replay, runbook, ownership and change process; transfer artefacts without hidden dependence on the consultant.

Purchase questions

Resolve objections by boundary and evidence, not slogans.

Do we have to replace our warehouse, orchestration or BI stack?

No by default. First test whether the scoped path can become reconstructible inside the existing stack.

What if our business rules are not documented?

Treat them as unresolved requirements, extract owners, and test representative cases. Do not turn undocumented habit into “truth”.

Will lineage slow processing?

It can add instrumentation, storage and query overhead depending on granularity and stack. Measure representative workloads before promotion; no universal percentage is claimed.

Can we start with one metric rather than the whole platform?

Yes. A small consequential path can expose semantics, ownership, failure handling and replay without hiding uncertainty in a large transformation programme.
