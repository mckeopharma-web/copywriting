The moment it becomes a project

You recognise one of these moments—or it is not the project yet.

These are diagnosable situations, not generic pain points. If none applies, do not force a CDM-automation engagement.

01

Lock time keeps drifting

The database closes later from study to study and the team cannot attribute where the elapsed time accumulates.

02

A manual step sits outside the plan

SDTM/ADaM preparation still depends on an undocumented hand-off, spreadsheet or one-person script.

03

A query blocks lock

The resolution history is distributed across messages rather than carried with the decision itself.

04

A transformation changed silently

Two extracts differ, but the rule version and execution path are not immediately reconstructible.

Consequences

The weak point is usually the exception, not the happy path.

The evidence chain breaks at the exception

If the nominal flow is versioned but the correction is only a free-text note, the rule, actor and rationale can become costly to reconstruct.

Bounded claim: architecture risk, not a measured incidence rate.

Automation hides the human decision

A rule can close a repetitive step while still preserving the decision boundary: rule version, input, output, exception, reviewer and approval.

The mechanism is designed for attributable decisions; it is not evidence of a shorter lock by itself.

Snapshots do not reconstruct a process

Archiving extracts preserves states. Reproducibility also needs the ordered transformations and the manually approved deviations that moved one state to the next.

Process

Four phases; every phase ends with an artefact and a decision.

1

Actual path

Map what the data really crosses, including manual steps.

Exit artefact: flow map + traceability breaks.

2

Pipeline

Move agreed transformations under source control and make their execution explicit.

Exit artefact: versioned pipeline + lineage.

3

Exceptions

Replace scattered manual corrections with a typed review queue.

Exit artefact: exception queue + replay test.

4

Handover

The client team executes the bounded lock workflow with the runbook.

Exit artefact: lock runbook + acceptance record.

Work modules

Executable rules, thresholds, recorded failures and release/lock gates.

Exceptions

Lock

Questions

Resolve the questions that change scope, responsibility or data handling.

Can this be done while a study is in progress?

Yes, when the in-flight workflow can be protected from uncontrolled change and a closed or test dataset is available for bounded replay and acceptance tests. The deployment sequence is agreed with the sponsor.

Does automation replace the Clinical Data Manager?

No. The design automates repeatable transformations and routes exceptions to accountable review. It is deliberately not a system for silently automating clinical judgement or statutory responsibility.

Do we need to change EDC?

No. EDC selection or migration is explicitly outside this scope. The engagement starts from the extraction boundary and the downstream path you actually control.

How are patient data handled?

The default is client-controlled infrastructure. Development should use test, synthetic or appropriately pseudonymised data where possible, with access and retention agreed before processing.
