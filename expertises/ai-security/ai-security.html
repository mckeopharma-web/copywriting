AI Security, Assurance & DevSecOps

Security after deployment is too late to be a release control. Make it a condition of promotion.

Triggers

You recognise one of these moments—or it is not yet the assignment.

These are dated events, not generic anxiety. If none is present, the lower-cost answer may be to document the decision and wait.

01

Release ownership is unclear

A promotion is blocked because nobody can state whether the AI component, its tools and permissions were reviewed.

02

A customer asks for provenance

A due-diligence questionnaire asks for dependencies, versions and provenance—and there is no reusable SBOM or release receipt.

03

An agent gains a new connector

An MCP connector or tool was added quickly; its reachable data, credentials and side effects were never brought into the security boundary.

04

Security arrives after the decision

The audit lands at the end of the cycle, when remediation competes directly with the planned release date.

Consequences

The workaround is usually more scanning. The missing object is a decision gate.

A report is advisory

Moving a review earlier helps only if a named control can change the release decision. Otherwise the review still depends on someone noticing and acting.

The AI surface is wider than code

Agent tools, network access, identities, credentials and reachable data can create exposure without changing the application source tree.

Logs are not a decision record

Raw CI output can show what a tool printed. A release receipt must also bind the result to the artifact, policy, exception and accountable approver.

Proposition

Risk → Policy → Test → Evidence → Promote / Block.

The mechanism is a promotion policy that can be executed by the delivery chain. The goal is not “more scans”; it is a release decision with named controls, explicit exceptions and a retrievable evidence record.

Process

Four phases. Four stopping points with a usable artifact.

Surface

Inventory the real exposure, including agents, connectors, credentials and data reach. Output: system boundary + threat model.

Gate

Translate the controls that matter into blocking conditions in the existing delivery chain. Output: live release gate.

Evidence

Bind each promotion to its policy, results, exceptions, artifact identity and approver. Output: release decision record.

Handoff

Your team adds a control, handles a deliberate block and executes an exception without the consultant. Output: runbook + exception procedure.

Modules

Work blocks, selected by the risk boundary—not by a fixed checklist.

Threat modelling

NCSC’s August 2026 guidance names two threat-modelling inputs explicitly—the prompt, and the networks and services the agent can access—and says threat modelling should occur before deployment.

Agent isolation & permissions

NCSC describes a four-level network-isolation model for agentic AI, ranging from unrestricted network access to no external network access with the model hosted locally.

Supply chain

SBOM, dependency provenance, transitive dependency review, base images, secrets and policy exceptions. The chosen gate depends on the artifact and threat model.

Release proof

NCSC’s August 2026 guidance names two telemetry classes for agentic AI—agent traces or transcripts, and wider sandbox logs—and links them to real-time oversight and later investigation; it says logs should be protected and immutable where possible.

Intersection

The differentiator is the seam removed, not a pile of technologies.

Regulated operations, AI/data engineering, assurance and verifiable systems are useful together only when they reduce translation between the risk statement, the enforceable control and the evidence record.

Control ↔ pipeline

The person defining the gate can also reason about how it behaves in CI/CD and where it can fail operationally.

Requirement ↔ evidence

Controls are designed with the artifact that will later demonstrate the decision, rather than adding evidence after implementation.

AI surface ↔ permissions

Agent tools, connectors, identities and data reach are handled as engineering objects, not questionnaire-only abstractions.

This is a mechanism claim. No universal speed, cost or risk-reduction effect is inferred from fewer handoffs.

Commitments

Guarantee the work product, never an authority’s decision.

Scope before billing

Scope, exclusions, dependencies and acceptance criteria are written before the first billed day. A scope change is a change request, not a surprise.

Deliverables meet written criteria

A deliverable that fails the agreed acceptance criteria is reworked against those criteria.

Reversibility

Code, configuration, schemas, decisions and journals are handed over. The design avoids a proprietary runtime dependency on the consultant.

Confidentiality boundary

Client data and evidence are explicitly classified before use: authorised, anonymised, synthetic or prohibited.

Human decision boundary

Each use case states where automation stops and where named human approval is mandatory.

No vulnerability-free promise

The mandate cannot guarantee absence of vulnerabilities. It can guarantee whether the agreed gate blocks an artifact that fails its named controls.

Questions

What still changes scope, responsibility or adoption.

Will a blocking gate stop the team?

It can, which is why the gate is calibrated against the risk that matters and ships with a traceable exception path. A gate that blocks what is easy to measure instead of what matters is a design failure.

Must we replace Jenkins, GitLab or GitHub Actions?

No. The decision policy is designed around the chain in place. Tool migration is a separate scope decision.

Do you fill customer security questionnaires?

The mandate produces reusable evidence—SBOM, provenance, boundary inventory and release records. Your organisation remains responsible for representations made to a customer.

Can we start with a short diagnostic?

Yes. The system-boundary inventory and threat model can be delivered as a bounded first step before implementing gates.
