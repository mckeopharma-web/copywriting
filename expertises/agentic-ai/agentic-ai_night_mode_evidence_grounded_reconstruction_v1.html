The production decision

Do not start with another agent framework. Start with the operating boundary.

OBJECTIVE → CONTEXT → STATE → ACTION AUTHORITY → TOOL / SIDE EFFECT → EVALUATION → HUMAN OVERSIGHT → TRACE → RELEASE DECISION

The architecture should make consequential actions explicit: who delegates authority, which tools and data are in scope, what state persists, which conditions require review, what gets logged, and what evidence is required before promotion.

When this becomes a CTO problem

The demo works. The operating questions do not.

Authority

The agent can call tools, but nobody can state its effective authority.

Permissions live partly in prompts, application code, connector configuration and human convention.

Replay

An incident happens, but the execution cannot be reconstructed end to end.

Inputs, retrieved context, tool calls, policy decisions, state changes and human interventions are not tied into one trace.

Evaluation

A model, prompt or tool changes, but release confidence is subjective.

There is no representative regression set, adversarial suite, grading contract or promotion threshold.

Human control

Human review exists, but the escalation boundary is implicit.

The system does not clearly distinguish what may execute autonomously from what must be reviewed, denied or rolled back.

Mechanism evidence

In a 2026 preprint’s compromised-model evaluation, an authorization layer enforced outside the model reduced AgentDojo exfiltration from 75–100% to 0% across four domains and blocked all 544 evaluated InjecAgent data-stealing cases.2

The commercially relevant implication is bounded: permission architecture can be evaluated as a system property instead of being left entirely to model behavior. It does not prove universal prompt-injection prevention.

Boundary: preprint benchmark result on the paper’s evaluated scenarios; utility trade-offs were also observed and remain part of the engineering decision.

Delivery method

Eight modules from authority boundary to handover.

1. Objective & Consequential-Action Boundary

Define the job, critical decisions, side effects, non-goals, failure modes and acceptance evidence.

2. Context & Retrieval Contract

Define admissible sources, context construction, provenance, minimization, freshness and retrieval failure behavior.

3. State & Governed Memory

Separate transient context, persistent memory, checkpoints and system-of-record state; define retention and mutation rules.

4. Tools, Identity & Authority

Map capabilities, delegation, permissions, secrets, connectors and external side effects; enforce critical boundaries outside the model where justified.

5. Orchestration & Handoffs

Define routing, supervisor/sub-agent relationships, handoff contracts, retry policy and failure containment.

6. Evaluation & Promotion Gates

Build golden tasks, adversarial cases, regression criteria, grader contracts and release thresholds tied to the intended use.

7. Observability, Human Review & Incident Control

Instrument trajectories, tool calls, policy decisions, review queues, denial paths, rollback and incident reconstruction.

8. Acceptance Evidence & Capability Transfer

Run acceptance, document residual risk, transfer runbooks and ownership, and leave the team with reusable technical assets.

Three acceptance outcomes

What the operating team should be able to do at handover.

Explain and constrain authority

Identify what each agent, tool and delegated path may do—and where execution must stop or escalate.

Reproduce and evaluate behavior

Replay critical trajectories and evaluate changes against explicit cases and promotion criteria.

Operate without hidden ownership

Use traces, review queues, runbooks and release evidence without depending on undocumented assumptions.

Problem → engineering response

Ten recurring production gaps.

1 · Tool authority is implicit

Response: capability inventory, identity model, permission boundaries and deny/escalate paths.

2 · Memory mutates without governance

Response: state classes, write rules, retention, checkpoints and provenance.

3 · Prompt injection becomes an execution risk

Response: treat model output as untrusted decision input and place consequential authorization at the runtime boundary.

4 · Evaluation is demo-driven

Response: representative task sets, adversarial scenarios, regression grading and release thresholds.

5 · Handoffs lose intent or scope

Response: explicit handoff contracts, delegated authority limits and state-transfer rules.

6 · Incidents cannot be replayed

Response: trajectory, context, tool-call, policy-decision and human-review evidence in one reconstructible chain.

7 · Human oversight is ceremonial

Response: define which decisions require approval, what evidence the reviewer receives and what happens on timeout or denial.

8 · Model changes bypass release discipline

Response: versioned evaluation, change triggers, promotion gates and rollback criteria.

9 · Connectors broaden the blast radius

Response: least-privilege credentials, scoped tools, secrets handling, network/data boundaries and auditable side effects.

10 · The prototype has no operating owner

Response: ownership matrix, runbooks, alerts, SLO-relevant signals and handover acceptance.

FAQ

Questions that change the architecture.

Do you build with MCP?

Yes where MCP is the appropriate tool/context interface, but the production question remains authority, data exposure, connector trust, observability and evaluation—not protocol adoption by itself.

Do agents need fully autonomous execution?

No. Autonomy is a design variable. Some actions can be automatic, others can require approval, and some should be denied by policy.

Can you guarantee prompt-injection immunity?

No. The engagement can reduce exposed authority, implement runtime controls, test attack scenarios and produce release evidence. It cannot prove absence of every future attack.

What stack do you work with?

Python, FastAPI, MCP, RAG, evaluation harnesses and PostgreSQL are current core components, with infrastructure and security tooling selected to the production boundary.

What does the team keep?

The scoped accepted artifacts: architecture decisions, evaluation assets, permission and state models, runbooks, evidence paths and ownership documentation.
